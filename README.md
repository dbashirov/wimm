# wimm

**Личные финансы под вашим контролем.**

wimm — веб-приложение для самостоятельного размещения: учёт доходов и расходов, кошельки в разных валютах, переводы и аналитика по категориям. Данные хранятся в вашей PostgreSQL, а интерфейс работает на серверных Go-шаблонах с частичными обновлениями через htmx.

**Go · PostgreSQL · htmx · Tailwind CSS · daisyUI**

## Возможности

- **Кошельки.** Отдельные счета с валютой и балансом, настройка порядка, скрытие и выбор кошелька по умолчанию.
- **Доходы и расходы.** Категории, дата и описание операции, редактирование прямо в списке, фильтры по кошельку, категории, типу и периоду.
- **Переводы.** Перемещение средств между кошельками; для разных валют задаются суммы списания и зачисления.
- **Обзор финансов.** Балансы по валютам, месячная динамика и распределение доходов и расходов по категориям.
- **Отчёты.** Выбор кошельков, категорий и периода; группировка по дням, неделям, месяцам или годам с автоматическим подбором шага.
- **Личные аккаунты.** Регистрация, вход и изоляция данных пользователей.
- **Светлая и тёмная темы.** Переключение темы с сохранением выбора в браузере.

### Как учитываются деньги

Суммы хранятся в целых сотых долях валюты (`int64` / PostgreSQL `BIGINT`), без арифметики с плавающей точкой. Перевод представлен двумя связанными операциями. При переводе между разными валютами сумма зачисления вводится вручную.

Общий баланс на главной странице разделён по валютам. **Отчёт по категориям суммирует выбранные операции без конвертации валют** — для сопоставимых итогов выбирайте кошельки одной валюты.

## Быстрый старт

Для запуска через Docker понадобятся **Docker Compose v2** и установленный **goose v3** для применения SQL-миграций. PostgreSQL 16 и приложение запускаются в контейнерах; CSS собирается внутри образа.

Если Go уже установлен, goose можно установить так:

```bash
go install github.com/pressly/goose/v3/cmd/goose@v3.27.0
```

Убедитесь, что каталог с установленным бинарником (`$(go env GOPATH)/bin` по умолчанию) добавлен в `PATH`.

### 1. Получите исходный код

```bash
git clone https://github.com/dbashirov/wimm.git
cd wimm
```

### 2. Запустите PostgreSQL и примените миграции

```bash
docker compose up -d --wait postgres
export DB_URL='postgres://wimm:wimm@localhost:5432/wimm?sslmode=disable'
goose -dir migrations postgres "$DB_URL" up
```

**Приложение не применяет миграции автоматически.** Их нужно запускать вручную перед первым запуском и при обновлениях схемы.

### 3. Запустите приложение

```bash
docker compose up -d --build app
```

Откройте [localhost:8080](http://localhost:8080) и создайте аккаунт. При регистрации приложение создаст стартовый кошелёк и категории.

```bash
docker compose logs -f app
docker compose down
```

База сохраняется в Docker-томе `pgdata` между перезапусками. Обычный `docker compose down` не удаляет этот том.

Этот Compose-файл предназначен для локального запуска: он использует тестовые реквизиты БД и HTTP. Параметры приложения заданы непосредственно в [docker-compose.yml](docker-compose.yml); значения из `.env` их не переопределяют.

## Локальная разработка

Требования: **Go 1.25.6 или новее**, **PostgreSQL 16**, **goose v3**, **make** и **npm**. В Docker-сборке используется Node.js 22; если локального npm нет, `make css` использует контейнер `node:22-alpine`.

Из корня репозитория подготовьте окружение:

```bash
cp .env.example .env
# При необходимости измените DB_URL и остальные параметры в .env.
set -a
. ./.env
set +a
```

Go-приложение читает переменные окружения и **не загружает `.env` самостоятельно**. Приведённые команды экспортируют значения в текущую оболочку.

Запустите БД, примените миграции и соберите стили:

```bash
docker compose up -d --wait postgres
goose -dir migrations postgres "$DB_URL" up
make css
go run ./cmd/server
```

Если приложение уже запущено через Compose, сначала остановите его командой `docker compose stop app`, чтобы освободить порт 8080.

### Команды разработки

| Команда | Назначение |
| --- | --- |
| `make css` | Сборка CSS из шаблонов |
| `make css-watch` | Пересборка CSS при изменении шаблонов |
| `go run ./cmd/server` | Запуск HTTP-сервера |
| `go build ./...` | Проверка сборки всех пакетов |
| `go vet ./...` | Статический анализ |
| `go test ./...` | Все тесты, включая интеграционные |
| `go test -race ./...` | Тесты с детектором гонок |
| `go generate ./internal/storage` | Генерация моков интерфейсов хранилища |
| `goose -dir migrations postgres "$DB_URL" status` | Состояние миграций |

Шаблоны и статика встраиваются в бинарник через `go:embed`. После их изменения перезапустите `go run` или пересоберите бинарник. Сгенерированные файлы CSS не хранятся в Git, поэтому `make css` нужен перед первой сборкой приложения с полноценным интерфейсом.

### Тестирование

Тесты моделей, бизнес-логики и HTTP-обработчиков можно запустить без базы данных:

```bash
go test ./internal/model ./internal/service ./internal/handler
```

Интеграционные тесты `internal/storage` требуют работающего Docker: Testcontainers создаёт отдельный PostgreSQL 16 и применяет миграции. Локальная рабочая БД для них не используется.

Workflow [Deploy](.github/workflows/deploy.yml) при push в `main` выполняет `go vet` и `go test -race`, затем запускает деплой по SSH.

## Конфигурация

Образец окружения — [.env.example](.env.example). Значения по умолчанию ниже относятся к самому приложению; локальный Compose задаёт часть параметров отдельно.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DB_URL` | Обязательна | Строка подключения к PostgreSQL |
| `SERVER_ADDR` | `:8080` | Адрес HTTP-сервера |
| `CSRF_SECRET` | Случайный при старте | Секрет подписи CSRF-токенов, минимум 16 байт |
| `COOKIE_INSECURE` | Не задана | Только `true` разрешает передавать cookies по HTTP |
| `TRUSTED_PROXIES` | `127.0.0.1,::1` | IP-адреса или CIDR доверенных прокси через запятую |
| `HSTS` | `false` | `true` включает Strict-Transport-Security |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn` или `error` |
| `LOG_FORMAT` | `text` | `text` для разработки, `json` для структурированных логов |

Для постоянного `CSRF_SECRET` сгенерируйте значение и сохраните его в окружении:

```bash
openssl rand -base64 32
```

Без постоянного секрета после перезапуска ранее открытые формы могут получить ошибку проверки CSRF.

## Архитектура

Приложение использует стандартный `net/http`, серверный рендеринг и слоёную архитектуру:

```text
Браузер · HTML / htmx
          │
          ▼
       handler ───── session.Manager
          │                 │
          ▼                 │
       service              │
          │                 │
          ▼                 ▼
       storage · pgxpool → PostgreSQL
```

| Каталог | Ответственность |
| --- | --- |
| `cmd/server/` | Конфигурация, запуск сервера, завершение работы |
| `internal/handler/` | HTTP-маршруты, middleware, рендеринг страниц |
| `internal/service/` | Бизнес-логика, валидация, подготовка отчётов |
| `internal/storage/` | PostgreSQL-репозитории и интеграционные тесты |
| `internal/model/` | Доменные типы и точное представление денежных сумм |
| `internal/session/` | Сессии с хранением в PostgreSQL |
| `web/` | HTML-шаблоны, исходники CSS и встроенная статика |
| `migrations/` | SQL-миграции goose |
| `docs/` | Документация по эксплуатации и проектным решениям |

Интерфейс использует htmx 2, Tailwind CSS 3 и daisyUI 4; графики — Chart.js и ECharts. CSS собирается локально, а часть браузерных библиотек и шрифтов загружается с внешних CDN.

Пароли хешируются bcrypt. Сессии хранятся на сервере; реализованы CSRF-защита, проверка cross-origin запросов, ограничение частоты входа и регистрации, защитные HTTP-заголовки. Доступ к данным ограничивается пользователем, а составные внешние ключи дополнительно проверяют принадлежность кошельков и категорий.

## Развёртывание

[Руководство по развёртыванию](docs/DEPLOY.md) описывает установку на VDS с PostgreSQL на хосте, приложением в Docker и nginx для HTTPS.

[docker-compose.prod.yml](docker-compose.prod.yml) используется как самостоятельный файл: он читает `.env`, использует сеть хоста и предполагает уже настроенную PostgreSQL. Перед запуском примените миграции, задайте постоянный `CSRF_SECRET`, установите `COOKIE_INSECURE=false` и настройте HTTPS. `HSTS=true` включается при работе через HTTPS.

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

### Проверка состояния

| Маршрут | Проверка | Ответ |
| --- | --- | --- |
| `GET /health` | HTTP-сервер отвечает | `200 ok` |
| `GET /ready` | Доступно подключение к PostgreSQL | `200 ready` или `503 not ready` |

`/ready` проверяет соединение с БД, но не актуальность схемы — статус миграций проверяется отдельно через goose.

Сервер поддерживает корректное завершение по `SIGINT` / `SIGTERM`, структурированные логи и идентификаторы запросов для диагностики.
